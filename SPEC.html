Diagnosis

Why your attachments keep breaking

Root cause

Mochi keys its generation cache on the entire concatenated source text plus options. Any edit — including a one-character typo fix — produces a new cache key, which triggers a fresh Azure call, writes a new mp3, and tombstones the old one as deleted?: true. Nothing reconciles the leftovers.

Card 913qMiTa in 基本情報 shows it cleanly. Its cache holds five speech entries whose keys are progressively longer prefixes of the same card — you typing it out — plus one more that differs only by a sプリント → スプリント correction. Result: five billed generations, four tombstones, one surviving file.

Across the three decks that pattern accounts for 505,304 characters sent to Azure where 231,769 were needed — a 2.18× overspend, and 8,958 dead attachment records. The worst single card, 領域, was regenerated 33 times.

The money is trivial (about $8 lifetime). The churn is not: every regeneration is a chance for a reference to end up pointing at a file that no longer exists, which is exactly the manual re-syncing you have been doing by hand.

Fix

Content-addressed, per-field, refcounted. Three changes, each removing one failure mode:

1. Address by hash. A blob's identity is sha256(normalised_text, voice, lang). Regenerating identical input is a cache hit, not a new file — so a typo fix that you then undo costs nothing and creates nothing.

2. Key per field, not per card. Mochi hashes the whole card, so editing line 3 invalidates the audio for lines 1–2. Hashing each field's resolved text independently means an edit only invalidates what actually changed.

3. Refcount, never tombstone. Blobs are immutable and shared; deletion happens only when the last reference drops. A reference can never dangle, because the blob it names cannot be mutated or removed while referenced.

4. Store the hash, never a path. No absolute path is ever written to the database. A row naming C:\DEV\WEB\hashigo\exports\… welds your library to one directory on one machine and breaks the moment anything moves — and exports/ is reference data, not source. This one is checkable mechanically rather than by convention: sweep every text column in every table and fail on any hit.

One correction to something I said earlier: I assumed content-addressing would win on storage through deduplication. Your data says otherwise — only 0.3–0.4% of files are byte-identical, because each clip has unique text. The win is idempotent regeneration and unbreakable references, which is the more valuable half anyway.

Data model

Review tracks, not review lists

The single most important structural finding: Mochi already tracks reverse review as a fully independent schedule, in a separate reverse-reviews array with its own intervals and durations. I had guessed it shared the forward schedule; it does not. 3,769 of 5,947 cards in 日本語 carry one, and four decks — 文法, 言葉, 漢字, 単語 — have the deck-level reverse flag set.

So a card does not have a review log. It has N independent tracks, each separately scheduled:

  • forward — always present
  • reverse — when the card or its deck enables it
  • cloze:{index} — per indexed cloze group

This generalises Mochi's three parallel arrays (reviews, reverse-reviews, cloze/reviews) into one concept, and makes the importer a straight mapping rather than a special case per array.

Your clozes are unused as a track, and more completely than draft 3 said. cloze/indexes is empty on all 7,716 cards, so every cloze reveals together — and cloze/reviews is present on 24 cards and empty on all 24. Draft 3 read that key's presence as 22 graded cards. It is not: there are zero cloze reviews in four years of history. Build the track abstraction now, because the importer needs it and it costs nothing — but know there is no observation anywhere in the corpus to test it against, and defer the indexed-cloze authoring UI until you want it.

Correction, measured 2026-08-19. Draft 4 said “a browser handed text/xml in an <audio> element will not play it, so this breaks playback outright”. That is false. One real corpus mp3 was handed to <audio src=blob:…> in Chromium 151 under five different labels — audio/mpeg, text/xml, application/octet-stream, the empty string, and audio/mpeg; codecs="mp3" — and all five reached canplay, reported the same 1.560 s duration and advanced the clock. Chromium sniffs the bytes and ignores the Blob type. So sniffing is still mandatory — the mime decides which element to build, the correct extension, and every download name — but the reason is data hygiene, not a silent playback outage. Set src, never <source type>.

Sides & direction

Side order is the exercise, not the layout

Both 単語 and 漢字 are four-side templates; 言葉, 文法 and New Vocab are three-side. Only the simplest are the front/back pair you'd assume. So a card is an ordered list of sides, and the model has to say what "reverse" means for a list of four.

Forward is the authored order. Reverse is a declared permutation, defaulting to the reversed list — which reproduces today's behaviour exactly, and gives any single template an escape hatch without introducing a second concept.

This works because the templates were authored symmetrically. Side 4 of 単語 is 意味 plus the emoji hint plus dictionary links: shown first, it asks you to produce the word from its meaning, which is what reverse review is for. The alternative — separate recognition and production templates, as Anki does with card types — is more machinery for the same outcome, and FSRS already treats the two directions as independent tracks, capturing that production is the harder skill.

Read this before building the renderer or the review UI

Drafts 1–6 described the four sides as structure. They are a produce-then-verify drill, and the ordering carries the pedagogy. Stated by Zach 2026-08-19 and confirmed against the templates:

単語. Reading is a boolean, and it switches the scaffolding. Side 1 shows Reference outright when it is true; side 2 wraps it in a cloze when it is false, alongside {{<furigana><<単語>></furigana>}} — also a cloze — and <<Speech>>. So the reading is hidden: he sees the kanji, recalls whether each mora is high or low, says it aloud, and only then reveals and compares against the audio. Side 3 repeats the exercise at sentence length with 例文 + Audio.

漢字. Identical shape: Kanji → <draw> canvas → Reading → Meaning. Draw it from memory, then see the answer. No audio on this template at all.

The hard requirement that follows: audio must never autoplay when a side appears. It fires on the cloze reveal, after production. Autoplay is the default in most flashcard renderers and it silently destroys the entire exercise by giving away the contour before he has produced it. This is a correctness requirement, not a preference.

The same rule governs the reverse permutation: reversing a template must not place a verification side before the production side it verifies. A permutation that is structurally valid can still be pedagogically broken.

Answer leak in reverse mode

Side 4 carries [Jisho](https://jisho.org/search/<<Kanji>>). The link text is safe, but the URL contains the answer. Any renderer that exposes URLs on hover, long-press, or a status bar leaks the card before you've recalled it. In reverse mode, defer link rendering to the answer side.

Reverse-review resolution

Mochi's review-reverse? is a two-state boolean, so "unset" and "deliberately off" are indistinguishable — which is why the deck setting has to win. There is no way to express an intentional exception. Making the card setting three-state removes the limitation:

Card valueResolves to
inherit — defaultWhatever the deck says, walking up the tree; workspace default off
onReverse, regardless of deck
offNo reverse, even when the deck says on

Decks take the same three states, so a subdeck can override its parent. The result: 単語's 3,702 cards all reverse by inheritance, and flipping one card to off keeps it off.

Importer rule — do not orphan history

Map review-reverse? = true to on, and absent or false to inherit. Then enforce: any card with a non-empty reverse-reviews array must resolve to on, or 43,083 review records lose their track.

And permanently: setting a card to off makes its reverse track dormant, not deleted — retained, not scheduled. No scheduling toggle should ever destroy four years of history.

Scheduling

Choose the algorithm by measurement

The default move would be "Mochi uses FSRS, so use FSRS." That's an assumption, and there is no need to assume — 102,020 graded reviews, each with the interval that preceded it, is a large and clean test set. Ship the scheduler that wins on your data.

That backtest has now been run. The two boxes below are what it settled; the rest of this section is the method, and the one thing it declined to settle.

Settled — FSRS-6, capped at 365 days, target retention 0.90

Algorithm: FSRS-6, fitted to your own history rather than shipped with population defaults.

Maximum interval: 365 days. A policy ceiling, not a data limit, and it happens to sit exactly where the evidence stops being evidence: the longest gap ever actually observed in this corpus is 454 days, so any schedule beyond that is extrapolation off the end of the support the fit was measured on. Raise it deliberately later if you want longer intervals — do not let a model fitted on censored data pick 1,000 days on its own.

Target retention: 0.90. Draft 4 said 0.95 and justified it by noting that realised retention is 96.24%, so a 0.95 target “roughly ratifies what you already do”. That inference was wrong and the number has changed. Realised retention tells you where the old scheduler landed, not what the new one will schedule. Mochi reaches 96.24% using intervals FSRS considers too long for 95%, so adopting FSRS at 0.95 shortens intervals. Measured under the 365-day cap above, against a realised 69.2 reviews/day over the last 90 active days (scripts/capped-load.ts):

Uncapped, 0.90 wants a median interval near 1,000 days — twice beyond the longest gap ever observed, since no review in the corpus follows an elapsed interval longer than 454 days. Capped at 365 the median is 365 days, inside measured territory. Below 0.90 the cap does the work rather than the target (81–87% of tracks clipped at 0.85), so going lower means raising the cap too, and then the schedule is extrapolating again. Target retention stays a per-deck setting.

Binary grades — a design decision, not a data limitation

Hashigo records remembered / forgot and nothing else. Anki's four-button Again / Hard / Good / Easy was considered and rejected, and Mochi's own founder reached the same conclusion. Binary maps onto FSRS as Again = 1 and Good = 3; there is no grade column to widen later.

The consequence is structural and belongs in writing before someone tries to fix it. FSRS-6's w[15] (Hard penalty) and w[16] (Easy bonus) apply only at ratings 2 and 4, so they are unreachable — in this corpus and in any future one. They are frozen at their published defaults, permanently, and no measured number depends on them; w[1] and w[3], the initial stabilities for Hard and Easy, are frozen alongside them for the same reason. This is not "unfitted for want of data". More history will never reach them.

The upside deserves stating rather than being treated as a limitation: the scheduler is fitted on exactly the signal it receives in production, so there is no train/serve distribution shift. A four-button model fitted on four-button history and then fed binary grades would have one.

Backtest, not A/B

A/B testing a scheduler doesn't work in practice: each arm needs months, and the signal is confounded by ordinary life — a busy fortnight is indistinguishable from a bad algorithm. Offline backtesting avoids both problems. Replay the real history and score how well each candidate predicted what actually happened, using log loss and RMSE of predicted recall probability against your true grades. This is the methodology FSRS itself was validated with.

Candidates: SM-2 (Anki classic), FSRS-6 with stock parameters, FSRS-6 fit to your history, and a naive fixed-multiplier as a sanity floor. If SM-2 wins, ship SM-2.

Known limitation — state it, don't hide it

The intervals in the log are the ones Mochi chose, so the sample is selection-biased: there is no observation of what would have happened at intervals you were never shown. Backtesting discriminates well between algorithms on observed data, but it is not ground truth for a scheduler that would have behaved very differently. Treat the result as strong evidence, not proof.

Draft 3 asked the backtest to quantify that saving and name a recommended default. It ran, and it declined to name one: 5 of its 17 free parameters land on clamp boundaries and wildly different weight vectors score within 0.0006 of each other, so a "recommended default" would have been an artefact of the fit rather than a finding. The saving draft 3 anticipated needs 0.85, and 0.85 needs the cap raised as well — at which point the schedule is extrapolating past its evidence.

Calibrate expectations on the algorithm too: fitted FSRS-6 scores 0.1905 held-out log loss against a constant-base-rate model's 0.2111, which is roughly a 10% improvement over a model with no inputs at all. Nobody should expect leaving Mochi to feel like a better scheduler. The wins in this project are the four problems at the top of it.

Target retention stays a setting — per deck, since 漢字 and 基本情報 have different stakes — defaulting to the 0.90 above.

Wiki-links are 56% of your corpus

Draft 1 called references unused, based on a bad sample. In fact 4,335 cards carry 8,744 wiki-links, mostly in the form [[display|card-id]] — and the pattern is morphological decomposition: ~に越したことはない links to 越す; ～に引き換え links to both 引く and 換える. Two links per card is the commonest case, because a two-kanji compound points at both components.

This is load-bearing. A parser that misses it renders over half your cards with broken links. Mochi also stores it the rename-safe way — stable ID plus cached display text — so that design is inherited, not invented.

The syntax has three forms, and draft 3 counted only the first: [[display|card-id]] — 8,690 · [[card-id]] — 46 · [[|card-id]] — 8. That is 8,744 links across 4,335 cards, and all 54 of the extra ones resolve to real cards. A matcher written for the piped form alone silently drops 54 real edges, which the @ picker and every backlink view would then be missing.

Two different sets of numbers, which draft 3 read as one

Links exist twice in the export: as syntax inside the text, and as a references array on the card. The two do not agree, and draft 3 put "8,690 wiki-links" and "7,763 of 7,771 resolve" in the same paragraph as though they described one measurement.

Parsed links in text: 8,744 occurrences, of which 18 are unresolved, pointing at 15 distinct missing targets.

The references array: 7,771 entries, of which 8 are unresolved, pointing at 7 distinct missing targets. The 7,763 figure belongs to this set and to nothing else.

And one of those 8 is not a deck you failed to export. Card gN7K9IpR writes [[**enactment**|zeeUDLTL]], and Mochi's own reference extractor mis-parsed the bold markers and stored the literal string enactment as a card id. Seven genuine unexported targets, one Mochi bug — worth knowing because Hashigo must not reproduce it. The rule stands either way: an unresolved link renders as plain text and is never dropped.

The invisible character that is not corruption

3,016 LEFT-TO-RIGHT MARKs, every one of them deliberate

Mochi could not parse two wiki-links written immediately next to each other, so you worked around it by wedging an invisible U+200E LEFT-TO-RIGHT MARK between them. That is how a multi-kanji compound points at each of its components — written out, with the mark shown as ‹lrm›, it is [[引く|…]]‹lrm›[[換える|…]].

Measured: 3,016 marks across 2,504 cards, of which 2,911 sit exactly between two adjacent links — the ]]‹lrm›[[ shape. This is recorded here because to anyone reading the data cold it is indistinguishable from the zero-width spaces in your tag list, which are corruption. These are not. Stripping them as a cleanup would destroy 2,911 deliberate separators.

Hashigo parses adjacent links natively, so the mark is no longer necessary on new cards. Existing marks are preserved verbatim in stored values regardless — it is your text, and removing it is a separate, deliberate migration rather than something the importer does on the way past. The one place invisible characters are dropped is the search index, which is a read-time projection and never the stored value.

Three parser traps

1. --- and ___ are different. The first separates card sides; the second is a horizontal rule inside a side. Conflating them silently restructures your cards.

2. Constructs nest, and resolve inside-out. Your 単語 template contains {{<furigana><< 単語 >></furigana>}} — a cloze wrapping a ruby tag wrapping a field. Order is fixed: resolve fields, then tags, then cloze.

3. Fields appear inside unquoted HTML attributes. Your 数字 template has <input value=<<NoComma>>>. A naive HTML parser will mis-tokenise that. Interpolate before parsing markup, not after.

There are two generation surfaces, and draft 1 only had one

The DAG above covers typed fields — declared on the template, with a source pointer and an options object. But generators are also written inline in card content, 545 times: <speech lang="jp"> (287), <ai> (125), <translate from="ja" to="en"> (106), <furigana> (19), <image> (8).

Both surfaces must feed the same content-addressed cache, keyed on inner text plus attributes. That is in fact why Mochi's component-cache is keyed by text rather than by field id — one cache, two callers.

Normalise language codes on import: inline tags use lang="jp" while field options use ja-JP. Same language, two spellings, one of them not valid BCP-47.

The trap Mochi documents as a gotcha

In Mochi, a dynamic field only generates if it appears in the template markdown — so a field that exists purely as an input to another field silently never resolves. That is a leaked implementation detail, not a real constraint. Hashigo resolves the DAG from the field definitions themselves; template presence controls display only.

One subtlety the schema hides: 例文 is an AI field whose source is null, because its dependency is written inside the prompt text — "Example sentence using <<単語>> in Japanese". The resolver therefore has to extract <<field>> references from prompt strings too, or it will build an incomplete graph and generate in the wrong order.

The bare-word problem — this blocks accent generation on either provider

Deriving a pitch accent offline (pyopenjtalk, MIT, with Open JTalk under Modified BSD) has one rule that the corpus violates almost everywhere: run the analyser on the word with its particle attached, never on the bare word. OpenJTalk does not encode 平板 as 0 the way NHK and OJAD dictionaries do — it returns the mora count — so bare 尾高 and bare 平板 both come back as accent == mora_count and are indistinguishable. 学生 returns accent=4, moras=4; treating any non-zero accent as a downstep emits ^がくせい! and turns the commonest pattern in the language into 尾高 across most of the deck.

Measured on 日本語: of 3,860 単語/言葉 values, 3,788 (98.1%) are bare, with no particle. 72 carry one. So the rule cannot be applied as written. The fix is mechanical — append a probe particle (が) to determine the accent type, then emit notation for the bare word alone — but it has to be deliberate, and it must be tested against the 24,558 existing speech generations rather than assumed.

And one question that is pedagogy, not engineering. Bare 尾高 and bare 平板 are indistinguishable acoustically too, to a native listener as much as to a parser, because 尾高's drop lands on the following particle. 花 and 鼻 alone sound identical; 花が and 鼻が do not. If drilling that distinction matters, the audio itself needs a particle — which changes what gets spoken, not merely how it is generated. The 72 particle-carrying entries may already be that workaround.

Two smaller consequences. 23 entries are grammar patterns carrying placeholders (～に越したことはない, ...にも程がある): these hold multiple accent phrases, needing one ^ each, and the ～ and ... characters are presumably being read aloud in the current audio. And the schema needs a manual accent-override field from the start — dictionary-driven analysis will guess on rare words, proper nouns and novel compounds, and retrofitting a field over 7,716 cards is worse than adding one now. OJAD stays the manual ground-truth reference: its terms permit exactly that use and forbid the bulk scraping that would otherwise be tempting.

Services

TTS is reopened, because the audio is for accent

Correction, 2026-08-19 — the requirement changed under this section

Drafts 1–6 treated audio as “high-quality embeddable TTS” and settled on Azure because the export names Azure voices, so identical voices reproduce the existing audio exactly. That reasoning answered the wrong question. The audio exists for one purpose: 高低アクセント shadowing. Zach looks at the kanji, recalls whether each mora is high or low, says it aloud, and only then reveals the reading and listens. See Sides & direction — the template side order is that exercise, not layout.

Which inverts the Azure argument. The 4,055 existing ja-JP-NanamiNeural clips are only an asset if their accents are right; if they are wrong they are a liability, because a wrong accent drilled through spaced repetition is worse than no audio and hard to unlearn. Regenerating all of them costs nothing at this volume. Voice continuity stops being a reason to choose a provider; accent control becomes the only one.

Google Cloud TTS specifies pitch accent. Azure, as far as its documentation goes, does not. Google exposes CustomPronunciations with a PHONETIC_ENCODING_JAPANESE_YOMIGANA encoding taking explicit markup — ^ opens an accent phrase, ! marks the downstep, Tokyo dialect, at most one ! per phrase — and Google's own documentation uses exactly the case that matters: ^はし / ^は!し / ^はし! for 端 / 箸 / 橋.

Azure has no documented equivalent. What it does have, checked against primary sources rather than recall, is two candidate mechanisms and no specification for either:

  • <phoneme alphabet="sapi"> — ja-JP's phone set is Kana-based, and Microsoft's own ja-JP examples table carries a mark: 合成 → ゴ'ウセ, 所有者 → ショュ'ウ?ャ. The apostrophe goes after the affected syllable. But it is documented as stress, inherited from SAPI, which was built for a stress-timed language. Japanese has pitch accent, not stress. Whether a Japanese neural voice reads that apostrophe as an accent nucleus or as English-style emphasis is undocumented, and the words “accent”, “pitch” and “downstep” appear nowhere in the ja-JP material.
  • <prosody pitch> per mora — hand-shaping the contour, which one published experiment reports sounding natural. It can produce a downstep, but you are authoring a pitch curve rather than declaring a linguistic fact, and Microsoft's own guidance says prosody behaviour varies by voice.

Status: open, and one test decides it. Synthesise a known minimal pair — 箸 versus 橋 — through a ja-JP neural voice with the apostrophe in each position, and listen. If Azure honours it as a nucleus, Azure wins and the existing voice is kept for free. If it applies emphasis instead, Google's specified notation wins and the whole library gets regenerated. This cannot be settled by reading; it needs the key.

Google's side has an unverified claim too: its CustomPronunciations is documented but has not been run end to end here, and which voice tiers honour it is unknown. Test both before committing.

Furigana should move off the API entirely. A local morphological analyser (kuromoji, MeCab + UniDic) plus JMdict gives you offline readings you can correct yourself when they're wrong — strictly better than a remote call you cannot fix, and it removes a network dependency from card creation.

Review timestamps — the one that cannot wait

Every review you have ever done shares one clock time

All 102,020 review records carry the timestamp 15:00:00Z — exactly midnight JST. Mochi truncates to the date and stores JST midnight. There is not one single genuine time-of-day value in four years of history.

This is unrecoverable. Unlike everything else in this spec, it cannot be reconstructed later from the export, because the information was never written down. Every day that passes without full timestamps is a day of data you cannot get back — which is why it belongs in stage 1 rather than with the analytics work that will consume it.

Store each review's reviewed_at as a full instant with timezone offset — the offset matters, since a 23:00 review in Tokyo and a 23:00 review abroad are different facts about your day. duration already exists on 92,089 reviews and is kept as-is.

Imported history must be flagged time-unknown, not silently assigned midnight. Otherwise every chart grows a false spike at 00:00 and the time-of-day analysis is poisoned by its own migration.

What this unlocks, none of which is possible today: retention by hour of day, session detection by clustering reviews into sittings, honest reviews-per-hour throughput, and whether your accuracy actually drops late at night.

Dashboard — move it to stage 2

This one is worth building far earlier than it looks, because it is read-only over already-imported data and doubles as the import's verification. Mochi's own dashboard gives you known-good figures; if Hashigo's review counts, retention and study hours match them, the importer is correct. That is a far better test than any assertion I could write.

Every tile in your screenshot is computable straight from the review log — 活動 heatmap, 学習カード数, 累計, 復習数, 定着率, 復習時間, デッキの進捗 — with one exception: 復習予測, the forecast, needs the scheduler. Build the dashboard at stage 2 without that tile, and add it after the scheduler lands.

Two things worth adding that Mochi's version lacks: retention plotted against interval length, which is where over-studying becomes visible rather than merely true; and per-deck retention, since 96.2% overall hides real variation between 漢字 and 基本情報.

Hierarchical tags

You already use the convention — Dialect/Kansai is in the data. So tags are materialised paths: store the full string, index each prefix, and the sidebar tree plus arbitrary nesting depth both fall out of that with no schema change. Dialect/Kansai/Osaka works the day you type it.

Your tag list is quietly corrupted

Five tags carry a leading zero-width space (U+200B), which is invisible in any UI and splits four tags into indistinguishable pairs:

Mathematics (8 cards) vs ␣Mathematics (1) · Computing (2) vs ␣Computing (1) · Finance (1) vs ␣Finance (1) · Logic (1) vs ␣Logic (1) — plus ␣Buddhism (11), which has no clean counterpart at all.

Almost certainly pasted in from a web page. If you have ever wondered why a tag appears twice in the sidebar, this is why. The importer should NFKC-normalise, strip zero-width and format characters, trim, then merge the collisions — turning 23 tags into 19 real ones.

Ctrl+K search

The schema half is an FTS index over field values, card names, and tag paths. The real decision is the tokeniser, and it is a Japanese-specific trap: SQLite FTS5's default tokeniser splits on whitespace, so it cannot index Japanese at all. Use the trigram tokeniser, which handles CJK substring matching, or pre-segment with the same morphological analyser used for furigana. Either way it is a stage-1 choice, because it determines the table definitions.

Index the rendered display text, not the raw source. Searching the stored value makes [[意味|abc123]] match on abc123 and miss the word itself; searching the render finds what you can actually see. The stored value keeps its markup verbatim — the index is a read-time projection, and search and display have to share one projection or the two will disagree about what a card says.

One more Japanese-specific trap on top of the tokeniser: trigram has a floor of three characters, and the commonest search unit in Japanese is two — 意味, 勉強, 漢字, 日本. Measured against ground truth over the imported corpus, 意味 occurs on 3 cards, する on 228 and ない on 74, and the trigram index returns nothing at all for any of them. So a 1–2 character query falls back to a LIKE scan over body, name and tag paths. A leading wildcard could not use an index anyway, and 7,716 rows is a scan of no consequence — but it must cover bodies, not just names, because all three 意味 hits are in bodies.

@ reference, and create-if-missing

Half of this already exists: 8,744 links across 4,335 cards, stored as [[display|card-id]]. What's missing is only the authoring affordance — an @ picker that searches as you type and, on no match, creates the card and links it in one action.

That is precisely the mining workflow you described doing by hand: spotting a word inside an example sentence, pinning the card, and coming back later to make a 単語 card from it. With create-if-missing, the pin-and-return loop collapses into a single keystroke — and the new card arrives already linked to the sentence it came from, which is context you currently lose.

Reuse the search index from Ctrl+K rather than building a second one, and let the picker also create into a chosen deck and template, so a word mined on the train lands in 単語 with its generators queued.

Live analytics with insights

Feasible, and phase 2 is the right home. The mechanism is simpler than it sounds: the app already holds every review in local SQLite, so it computes the aggregates itself and sends only the summary — retention by interval bucket, by deck, by hour once timestamps exist, lapse distributions, forecast load — to a model for interpretation.

The design rule is: send aggregates, never the raw log. A summary of 102,020 reviews is a few kilobytes, which keeps the cost at effectively nothing and means your entire study history never leaves the device. Shipping raw rows would be both expensive and needless.

The stage-1 obligation is small but real: settle the shape of that aggregate now, so the queries feeding it are stable and the dashboard and the insight panel read the same numbers.

Build order

Sequenced by what unblocks what

This order is genuinely dependent — each stage needs the one before it, and the importer comes early because it turns your real data into the test fixture for everything after.

  1. Schema + importer. Read .mochi, land all 7,716 cards and 102,020 reviews, round-trip losslessly. Carries the schema half of every request in the previous section: full review timestamps, tag paths with normalisation, wiki-links, FTS tables, and the aggregate shape.
  2. Dashboard, read-only. Reproduce Mochi's figures from the imported data. This is the import's acceptance test — matching numbers means the import is right — and it's the first thing you can actually use. Forecast tile deferred to after the scheduler.
  3. Template engine. All fourteen constructs, with the three traps handled. Golden-file tested against your 10 real templates — 11 rows across the three exports, because oiaISYb2 (単語) is defined identically in both 日本語 and 基本情報, so the importer upserts by id.
  4. Renderer. Markdown plus the whitelisted elements — furigana, draw, input, cloze reveal.
  5. Scheduler backtest. Replay the imported history against the candidates, pick a winner, fit its parameters, and recommend a target retention per deck. Runs offline against stage 1's output — no UI needed, and it settles a decision everything after depends on.
  6. Scheduler. The winning algorithm, over tracks.
  7. Review UI. The screen you'll spend all your time in. Forecast tile joins the dashboard here.
  8. Search. Ctrl+K over the stage-1 index — earns its place before the editor, since the @ picker reuses it.
  9. Generation pipeline. DAG resolver for typed fields, inline-tag resolver for card content, content-addressed cache, Azure and LLM backends.
  10. Editor. Card and template authoring on phone and desktop, the @ picker with create-if-missing, and the tag sidebar.
  11. Sync. Last, because everything before it is verifiable on one device — and this is the piece that breaks Mochi on Android.

Phase 2: the live analytics board with generated insights, reading the aggregates defined in stage 1.

Settled

Resolved since draft 1

  • Reverse review keeps the whole-card flip. The templates were authored symmetrically, so reversal already produces real production practice. Modelled as an ordered side list with a default-reversed permutation, so a single template can deviate later without a second concept.
  • The six empty leaf decks are dropped by default — 副詞, 名詞, 形容動詞, 一段動詞, 形容詞, 五段動詞 — taking 45 decks to 39. This is the default rather than a flag you have to remember to pass. The English and 基本情報 roots hold no direct cards but are populated parents; they stay. If part-of-speech becomes worth filtering on, it belongs as a tag or field — a card can be both 動詞 and 敬語, but it lives in only one deck.
  • Reverse toggle is three-state, card beats deck. Preserves today's deck-wide behaviour by inheritance while allowing per-card exceptions, which Mochi's boolean cannot express.
  • The scheduler is FSRS-6 — chosen by backtest rather than assumed, fitted to your own history, capped at 365 days, targeting 0.90 retention. Target retention stays a per-deck setting; 0.90 is its default. It was set from projected daily load rather than from realised retention — 0.95 would be 1.9–3.0× the current workload — and the cap is what keeps 0.90 inside measured intervals.
  • Grades are binary: remembered / forgot. Anki's four-button Again / Hard / Good / Easy was considered and rejected. FSRS's w[15] and w[16] are therefore unreachable by design and are frozen rather than fitted — and in exchange the scheduler is trained on exactly the signal it is given in production.
  • Blobs are content-addressed and refcounted, and no absolute path is ever stored. Tombstoning is what left 8,958 dead attachment records in Mochi; refcounting cannot produce a dangling reference. The path rule is an acceptance check, not a convention.
  • The payloads live in BLOB rows inside a second SQLite database, not in one file per payload. Settled on measurement, in a real browser, over the whole 624.6 MiB of real audio: 10,816 individual OPFS files took 322.1 s to write and 10.60 ms per random read, while the same bytes as BLOB rows in one OPFS-backed file took 4.9 s and 0.54 ms. Re-measured since on a second machine — 19.30 ms against 0.52–0.60 ms per payload written, 14.31 ms against 0.15–0.25 ms per read — so the multipliers move (32×–65× write, 20×–95× read) and the ordering never does. Minutes of uninterruptible writing on first run versus seconds is the difference between an app that works on a phone and one that looks broken on it. The store is <database>.blobs.db, kept separate so the ~70 MB card database stays small, quick to sync and quick to rebuild; the directory store is kept for export and interop. Because blobs.hash means “ask the store” and never “look here”, the swap changed no row of any table.
  • Stale pre-template content is discarded on import — and reported. 3,159 templated cards carry 79,175 characters of hand-written text that predates their template, none of which matches what the template renders. It is dropped so the render has a single source of truth, and listed so it stays recoverable from the export.

Still to decide

  • Leech policy. needs-rereview? exists but its behaviour is undocumented, so the rule has to be designed rather than reverse-engineered from Mochi. Draft 3 said "one card, 81 reviews, nothing to preserve"; the flag is per track, and the real figures are 17 cards and 337 reviews — 1 forward, 16 reverse. Four times the sample, and still a design question rather than a migration one.
  • LLM choice for <ai> fields. Cost is noise at this volume, so pick on output quality. Same shape as the audio question, and worth resolving the same way: run the real emoji-gloss prompt over twenty words you already have generated output for, and compare against what Mochi produced. There are 19,710 such examples to draw the twenty from.
  • Sub-daily intervals. 7.6% of reviews come due within a day, which implies learning steps this spec hasn't defined. The backtest will show whether they earn their place.
