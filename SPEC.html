Diagnosis

Why your attachments keep breaking

Root cause

Mochi keys its generation cache on the entire concatenated source text plus options. Any edit — including a one-character typo fix — produces a new cache key, which triggers a fresh Azure call, writes a new mp3, and tombstones the old one as deleted?: true. Nothing reconciles the leftovers.

Card 913qMiTa in 基本情報 shows it cleanly. Its cache holds five speech entries whose keys are progressively longer prefixes of the same card — you typing it out — plus one more that differs only by a sプリント → スプリント correction. Result: five billed generations, four tombstones, one surviving file.

Across the three decks that pattern accounts for 505,304 characters sent to Azure where 231,769 were needed — a 2.18× overspend, and 8,958 dead attachment records. The worst single card, 領域, was regenerated 33 times.

The money is trivial (about $8 lifetime). The churn is not: every regeneration is a chance for a reference to end up pointing at a file that no longer exists, which is exactly the manual re-syncing you have been doing by hand.

Fix

Content-addressed, per-field, refcounted. Three changes, each removing one failure mode:

1. Address by hash. A blob's identity is sha256(normalised_text, voice, lang). Regenerating identical input is a cache hit, not a new file — so a typo fix that you then undo costs nothing and creates nothing.

2. Key per field, not per card. Mochi hashes the whole card, so editing line 3 invalidates the audio for lines 1–2. Hashing each field's resolved text independently means an edit only invalidates what actually changed.

3. Refcount, never tombstone. Blobs are immutable and shared; deletion happens only when the last reference drops. A reference can never dangle, because the blob it names cannot be mutated or removed while referenced.

One correction to something I said earlier: I assumed content-addressing would win on storage through deduplication. Your data says otherwise — only 0.3–0.4% of files are byte-identical, because each clip has unique text. The win is idempotent regeneration and unbreakable references, which is the more valuable half anyway.

Data model

Review tracks, not review lists

The single most important structural finding: Mochi already tracks reverse review as a fully independent schedule, in a separate reverse-reviews array with its own intervals and durations. I had guessed it shared the forward schedule; it does not. 3,769 of 5,947 cards in 日本語 carry one, and four decks — 文法, 言葉, 漢字, 単語 — have the deck-level reverse flag set.

So a card does not have a review log. It has N independent tracks, each separately scheduled:

  • forward — always present
  • reverse — when the card or its deck enables it
  • cloze:{index} — per indexed cloze group

This generalises Mochi's three parallel arrays (reviews, reverse-reviews, cloze/reviews) into one concept, and makes the importer a straight mapping rather than a special case per array.

Your indexed clozes are unused — cloze/indexes is empty on every card, so all your clozes reveal together as a single track. Build the track abstraction now because the importer needs it; defer the indexed-cloze authoring UI until you want it.

Sides & direction

Cards have four sides, not two

Both 単語 and 漢字 are four-side templates; 言葉, 文法 and New Vocab are three-side. Only the simplest are the front/back pair you'd assume. So a card is an ordered list of sides, and the model has to say what "reverse" means for a list of four.

Forward is the authored order. Reverse is a declared permutation, defaulting to the reversed list — which reproduces today's behaviour exactly, and gives any single template an escape hatch without introducing a second concept.

This works because the templates were authored symmetrically. Side 4 of 単語 is 意味 plus the emoji hint plus dictionary links: shown first, it asks you to produce the word from its meaning, which is what reverse review is for. The alternative — separate recognition and production templates, as Anki does with card types — is more machinery for the same outcome, and FSRS already treats the two directions as independent tracks, capturing that production is the harder skill.

Answer leak in reverse mode

Side 4 carries [Jisho](https://jisho.org/search/<<Kanji>>). The link text is safe, but the URL contains the answer. Any renderer that exposes URLs on hover, long-press, or a status bar leaks the card before you've recalled it. In reverse mode, defer link rendering to the answer side.

Reverse-review resolution

Mochi's review-reverse? is a two-state boolean, so "unset" and "deliberately off" are indistinguishable — which is why the deck setting has to win. There is no way to express an intentional exception. Making the card setting three-state removes the limitation:

Card valueResolves to
inherit — defaultWhatever the deck says, walking up the tree; workspace default off
onReverse, regardless of deck
offNo reverse, even when the deck says on

Decks take the same three states, so a subdeck can override its parent. The result: 単語's 3,702 cards all reverse by inheritance, and flipping one card to off keeps it off.

Importer rule — do not orphan history

Map review-reverse? = true to on, and absent or false to inherit. Then enforce: any card with a non-empty reverse-reviews array must resolve to on, or 43,083 review records lose their track.

And permanently: setting a card to off makes its reverse track dormant, not deleted — retained, not scheduled. No scheduling toggle should ever destroy four years of history.

Scheduling

Choose the algorithm by measurement

The default move would be "Mochi uses FSRS, so use FSRS." That's an assumption, and there is no need to assume — 102,020 graded reviews, each with the interval that preceded it, is a large and clean test set. Ship the scheduler that wins on your data.

Backtest, not A/B

A/B testing a scheduler doesn't work in practice: each arm needs months, and the signal is confounded by ordinary life — a busy fortnight is indistinguishable from a bad algorithm. Offline backtesting avoids both problems. Replay the real history and score how well each candidate predicted what actually happened, using log loss and RMSE of predicted recall probability against your true grades. This is the methodology FSRS itself was validated with.

Candidates: SM-2 (Anki classic), FSRS-6 with stock parameters, FSRS-6 fit to your history, and a naive fixed-multiplier as a sanity floor. If SM-2 wins, ship SM-2.

Known limitation — state it, don't hide it

The intervals in the log are the ones Mochi chose, so the sample is selection-biased: there is no observation of what would have happened at intervals you were never shown. Backtesting discriminates well between algorithms on observed data, but it is not ground truth for a scheduler that would have behaved very differently. Treat the result as strong evidence, not proof.

Wiki-links are 56% of your corpus

Draft 1 called references unused, based on a bad sample. In fact 4,323 cards carry 8,690 wiki-links in the form [[display|card-id]] — and the pattern is morphological decomposition: ~に越したことはない links to 越す; ～に引き換え links to both 引く and 換える. Two links per card is the commonest case, because a two-kanji compound points at both components.

This is load-bearing. A parser that misses it renders over half your cards with broken links. Mochi also stores it the rename-safe way — stable ID plus cached display text — so that design is inherited, not invented. 7,763 of 7,771 resolve inside these three exports; the remaining 8 point at decks you didn't export, so unresolved links must render as plain text rather than being dropped.

Three parser traps

1. --- and ___ are different. The first separates card sides; the second is a horizontal rule inside a side. Conflating them silently restructures your cards.

2. Constructs nest, and resolve inside-out. Your 単語 template contains {{<furigana><< 単語 >></furigana>}} — a cloze wrapping a ruby tag wrapping a field. Order is fixed: resolve fields, then tags, then cloze.

3. Fields appear inside unquoted HTML attributes. Your 数字 template has <input value=<<NoComma>>>. A naive HTML parser will mis-tokenise that. Interpolate before parsing markup, not after.

Generation

Fields form a dependency graph

Generated fields point at other fields as input, so generation is a DAG that must be resolved in topological order. Your 単語 template is the most involved case:

<<#Reading>>"}

There are two generation surfaces, and draft 1 only had one

The DAG above covers typed fields — declared on the template, with a source pointer and an options object. But generators are also written inline in card content, 545 times: <speech lang="jp"> (287), <ai> (125), <translate from="ja" to="en"> (106), <furigana> (19), <image> (8).

Both surfaces must feed the same content-addressed cache, keyed on inner text plus attributes. That is in fact why Mochi's component-cache is keyed by text rather than by field id — one cache, two callers.

Normalise language codes on import: inline tags use lang="jp" while field options use ja-JP. Same language, two spellings, one of them not valid BCP-47.

The trap Mochi documents as a gotcha

In Mochi, a dynamic field only generates if it appears in the template markdown — so a field that exists purely as an input to another field silently never resolves. That is a leaked implementation detail, not a real constraint. Hashigo resolves the DAG from the field definitions themselves; template presence controls display only.

One subtlety the schema hides: 例文 is an AI field whose source is null, because its dependency is written inside the prompt text — "Example sentence using <<単語>> in Japanese". The resolver therefore has to extract <<field>> references from prompt strings too, or it will build an incomplete graph and generate in the wrong order.

Services

Azure, settled by your own data

The exports name the voices outright: ja-JP-NanamiNeural, ja-JP-DaichiNeural, en-US-AIGenerate1Neural. Those are Azure Neural TTS voice IDs — so Mochi is an Azure customer, and using the same voices reproduces the audio quality you already have exactly. No listening test needed; I'd suggested one, and your data made it unnecessary.

Better: at your real rate — about 58,000 characters a year once regeneration churn is eliminated — Azure's free tier of 500,000 characters per month covers you roughly a hundred times over. Speech synthesis is, in practice, free.

Furigana should move off the API entirely. A local morphological analyser (kuromoji, MeCab + UniDic) plus JMdict gives you offline readings you can correct yourself when they're wrong — strictly better than a remote call you cannot fix, and it removes a network dependency from card creation.

Review timestamps — the one that cannot wait

Every review you have ever done shares one clock time

All 102,020 review records carry the timestamp 15:00:00Z — exactly midnight JST. Mochi truncates to the date and stores JST midnight. There is not one single genuine time-of-day value in four years of history.

This is unrecoverable. Unlike everything else in this spec, it cannot be reconstructed later from the export, because the information was never written down. Every day that passes without full timestamps is a day of data you cannot get back — which is why it belongs in stage 1 rather than with the analytics work that will consume it.

Store each review's reviewed_at as a full instant with timezone offset — the offset matters, since a 23:00 review in Tokyo and a 23:00 review abroad are different facts about your day. duration already exists on 92,089 reviews and is kept as-is.

Imported history must be flagged time-unknown, not silently assigned midnight. Otherwise every chart grows a false spike at 00:00 and the time-of-day analysis is poisoned by its own migration.

What this unlocks, none of which is possible today: retention by hour of day, session detection by clustering reviews into sittings, honest reviews-per-hour throughput, and whether your accuracy actually drops late at night.

Dashboard — move it to stage 2

This one is worth building far earlier than it looks, because it is read-only over already-imported data and doubles as the import's verification. Mochi's own dashboard gives you known-good figures; if Hashigo's review counts, retention and study hours match them, the importer is correct. That is a far better test than any assertion I could write.

Every tile in your screenshot is computable straight from the review log — 活動 heatmap, 学習カード数, 累計, 復習数, 定着率, 復習時間, デッキの進捗 — with one exception: 復習予測, the forecast, needs the scheduler. Build the dashboard at stage 2 without that tile, and add it after the scheduler lands.

Two things worth adding that Mochi's version lacks: retention plotted against interval length, which is where over-studying becomes visible rather than merely true; and per-deck retention, since 96.2% overall hides real variation between 漢字 and 基本情報.

Hierarchical tags

You already use the convention — Dialect/Kansai is in the data. So tags are materialised paths: store the full string, index each prefix, and the sidebar tree plus arbitrary nesting depth both fall out of that with no schema change. Dialect/Kansai/Osaka works the day you type it.

Your tag list is quietly corrupted

Five tags carry a leading zero-width space (U+200B), which is invisible in any UI and splits four tags into indistinguishable pairs:

Mathematics (8 cards) vs ␣Mathematics (1) · Computing (2) vs ␣Computing (1) · Finance (1) vs ␣Finance (1) · Logic (1) vs ␣Logic (1) — plus ␣Buddhism (11), which has no clean counterpart at all.

Almost certainly pasted in from a web page. If you have ever wondered why a tag appears twice in the sidebar, this is why. The importer should NFKC-normalise, strip zero-width and format characters, trim, then merge the collisions — turning 23 tags into 19 real ones.

Ctrl+K search

The schema half is an FTS index over field values, card names, and tag paths. The real decision is the tokeniser, and it is a Japanese-specific trap: SQLite FTS5's default tokeniser splits on whitespace, so it cannot index Japanese at all. Use the trigram tokeniser, which handles CJK substring matching, or pre-segment with the same morphological analyser used for furigana. Either way it is a stage-1 choice, because it determines the table definitions.

Search should cover field values rather than rendered output — you want to find a word by its reading even when the card displays only kanji.

@ reference, and create-if-missing

Half of this already exists: 8,690 links across 4,323 cards, stored as [[display|card-id]]. What's missing is only the authoring affordance — an @ picker that searches as you type and, on no match, creates the card and links it in one action.

That is precisely the mining workflow you described doing by hand: spotting a word inside an example sentence, pinning the card, and coming back later to make a 単語 card from it. With create-if-missing, the pin-and-return loop collapses into a single keystroke — and the new card arrives already linked to the sentence it came from, which is context you currently lose.

Reuse the search index from Ctrl+K rather than building a second one, and let the picker also create into a chosen deck and template, so a word mined on the train lands in 単語 with its generators queued.

Live analytics with insights

Feasible, and phase 2 is the right home. The mechanism is simpler than it sounds: the app already holds every review in local SQLite, so it computes the aggregates itself and sends only the summary — retention by interval bucket, by deck, by hour once timestamps exist, lapse distributions, forecast load — to a model for interpretation.

The design rule is: send aggregates, never the raw log. A summary of 102,020 reviews is a few kilobytes, which keeps the cost at effectively nothing and means your entire study history never leaves the device. Shipping raw rows would be both expensive and needless.

The stage-1 obligation is small but real: settle the shape of that aggregate now, so the queries feeding it are stable and the dashboard and the insight panel read the same numbers.

Build order

Sequenced by what unblocks what

This order is genuinely dependent — each stage needs the one before it, and the importer comes early because it turns your real data into the test fixture for everything after.

  1. Schema + importer. Read .mochi, land all 7,716 cards and 102,020 reviews, round-trip losslessly. Carries the schema half of every request in the previous section: full review timestamps, tag paths with normalisation, wiki-links, FTS tables, and the aggregate shape.
  2. Dashboard, read-only. Reproduce Mochi's figures from the imported data. This is the import's acceptance test — matching numbers means the import is right — and it's the first thing you can actually use. Forecast tile deferred to after the scheduler.
  3. Template engine. All fourteen constructs, with the three traps handled. Golden-file tested against your 11 real templates.
  4. Renderer. Markdown plus the whitelisted elements — furigana, draw, input, cloze reveal.
  5. Scheduler backtest. Replay the imported history against the candidates, pick a winner, fit its parameters, and recommend a target retention per deck. Runs offline against stage 1's output — no UI needed, and it settles a decision everything after depends on.
  6. Scheduler. The winning algorithm, over tracks.
  7. Review UI. The screen you'll spend all your time in. Forecast tile joins the dashboard here.
  8. Search. Ctrl+K over the stage-1 index — earns its place before the editor, since the @ picker reuses it.
  9. Generation pipeline. DAG resolver for typed fields, inline-tag resolver for card content, content-addressed cache, Azure and LLM backends.
  10. Editor. Card and template authoring on phone and desktop, the @ picker with create-if-missing, and the tag sidebar.
  11. Sync. Last, because everything before it is verifiable on one device — and this is the piece that breaks Mochi on Android.

Phase 2: the live analytics board with generated insights, reading the aggregates defined in stage 1.

Settled

Resolved since draft 1

  • Reverse review keeps the whole-card flip. The templates were authored symmetrically, so reversal already produces real production practice. Modelled as an ordered side list with a default-reversed permutation, so a single template can deviate later without a second concept.
  • The six empty leaf decks are dropped — 副詞, 名詞, 形容動詞, 一段動詞, 形容詞, 五段動詞. The English and 基本情報 roots hold no direct cards but are populated parents; they stay. If part-of-speech becomes worth filtering on, it belongs as a tag or field — a card can be both 動詞 and 敬語, but it lives in only one deck.
  • Reverse toggle is three-state, card beats deck. Preserves today's deck-wide behaviour by inheritance while allowing per-card exceptions, which Mochi's boolean cannot express.
  • The scheduler is chosen by backtest, not assumed. Target retention becomes a per-deck setting.

Open

Still to decide

  • Leech policy. needs-rereview? exists and 81 reviews carry rereview?, but the behaviour is undocumented. Only one card currently carries the flag, so there is nothing to preserve — design a rule rather than reverse-engineering Mochi's.
  • LLM choice for <ai> fields. Cost is noise at this volume, so pick on output quality. Same shape as the audio question, and worth resolving the same way: run the real emoji-gloss prompt over twenty words you already have generated output for, and compare against what Mochi produced.
  • Sub-daily intervals. 7.6% of reviews come due within a day, which implies learning steps this spec hasn't defined. The backtest will show whether they earn their place.
